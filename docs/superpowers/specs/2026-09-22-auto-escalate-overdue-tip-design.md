# 超时自动升级与超时提醒设计

**日期：** 2026-09-22  
**状态：** 待用户审阅  
**范围：** SLA 时限调整、超时自动升级、首页「我的待处理超时工单」全局提示

---

## 1. 背景

当前工单超时后仅展示「已超时」，需人工调用升级接口；紧急/高优先级 SLA 分别为 2h / 8h，与业务期望不一致。首页缺少「我负责且已超时」的强提醒。

## 2. 已确认决策

| 项 | 选择 |
|----|------|
| SLA | 紧急 **1h**，高 **4h**；中 24h、低 72h 不变 |
| 自动升级范围 | 全部优先级，SLA 到期即自动升级 |
| 升级对象 | 当前处理组主管；处理人已是主管 → 系统管理员 |
| 触发方式 | 请求时懒同步（列表 / 详情 / pending-count 等读路径） |
| 超时提醒 | 全局提示框，`duration: 0`，仅点关闭；关闭后仅当数量变化再弹 |

## 3. 后端

### 3.1 优先级种子

更新 `PRIORITIES` 并在 seed / 启动同步中把已有「紧急」「高」记录的 `sla_hours` 写成 1 / 4。

### 3.2 自动升级

- 抽取与手动升级相同的核心逻辑（转主管/管理员、记 `escalate` 日志、重置 `sla_started_at`、状态回 `processing`；是否改紧急优先级与现网手动升级保持一致）。
- 在现有同步钩子中：对开放状态工单若 `sla_info.slaState == overdue`，执行一次自动升级；同请求内幂等（已升级且 SLA 已重置则不再升）。
- 手动 `/escalate` 可保留作兜底。

### 3.3 我的超时数量

- 接口（新建或扩展 pending-count）：返回当前用户作为 **assignee**、开放且 SLA 已超时的工单数。
- 调用前先跑自动升级同步，再统计「升级后仍属我且超时」或「同步前我的超时」——以 **assignee=当前用户且同步后仍 overdue / 处理中类开放** 为准；推荐：**同步前统计「我负责且已过 deadline」的数量**，用于提醒处理人；同步升级可能把单转给主管，主管侧数量增加。

**提醒统计口径（定稿）：**  
`assignee_id == 当前用户` 且状态 ∈ 开放处理态，且 `slaState == overdue`（在本请求自动升级**之前**统计并返回；升级在统计后执行，或分别返回 `overdueCount` 供提醒、升级后刷新列表）。

为避免「一打开页面就升级走导致看不到自己超时」，采用：

1. 先按当前数据算 `myOverdueCount`（负责人是我且已超时）  
2. 再执行自动升级  
3. 接口同时返回 `myOverdueCount`（升级前）供提示；列表下次加载看到升级结果  

## 4. 前端

- 布局挂载后（及定期 / 切回前台时可选）拉取 `myOverdueCount`。
- `count > 0` 时用 `ElNotification`（或等价）：标题「超时提醒」，内容「我的待处理超时工单：N」，不自动关闭。
- `sessionStorage`（或内存）记录上次关闭时的 `count`；仅当 `count !== lastDismissedCount` 再弹。
- 点击通知正文可跳转 `/ticket/list` 并带 `overdue=1` 筛选（若路由支持）。

## 5. 测试

- 紧急/高 `sla_hours` 为 1/4。  
- 人为把 `sla_started_at` 拨早后，读列表触发自动升级到主管；主管是处理人时升到 admin。  
- 客户账号不弹超时提醒；处理人有超时单时弹出，关闭后同数量不再弹，数量变化再弹。

## 6. 不做

- 独立定时任务 / 消息推送中心  
- 改中/低 SLA 数值  
- 邮件 / 短信通知  

## 7. 验收

1. 紧急满 1h、高满 4h 后，无需点升级即转主管（或管理员）。  
2. 登录后若有我的超时单，出现不可自动关闭的全局提示；点关闭后同数量不重复弹。  
3. 现有工单 CRUD / 客户确认 / 回访回归通过。
